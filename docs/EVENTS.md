# MCP Events

This endpoint implements the [OpenAI webhook integration](https://developers.openai.com/plugins/build/mcp-events) and [experimental Events proposal](https://github.com/modelcontextprotocol/experimental-ext-triggers-events/blob/main/docs/design-sketch-proposal.md). It advertises `capabilities.events` on MCP 2026-07-28 `server/discover` over both stdio and Streamable HTTP; rmcp 3.5.1's typed capabilities lack the field, so the stdio service adapter and the HTTP middleware add it to the discovery response. `events/list`, `events/subscribe` and `events/unsubscribe` are served to every client and protocol revision. Clients without Events support (for example Claude) simply use `wait_execution`/`read_execution`.

The subscription store and delivery workers live in the single broker, not in a frontend. Any number of stdio and HTTP frontends can be connected; each forwards subscribe/unsubscribe to the broker, and a subscription keeps delivering when the frontend that created it disconnects.

`events/list` defines `execution.events` with delivery `["webhook"]`. Subscribe using `name`, `arguments: {session_id, execution_id?}`, `delivery: {mode:"webhook", url, secret:"whsec_<base64>"}`, optional `cursor`, and optional `ttlMs`. Unsubscribe uses the same name, filter arguments and delivery URL. Keys are decoded to 24–64 bytes. No stream/poll delivery, protocol `gap`/`terminated` control messages, or invented aliases are exposed.

The OS UID is the sole trusted owner of this personal endpoint; whatever authenticates clients in front of it (SSH, Tunnel, Cloudflare Access) must admit only that person. The server does not accept a client-supplied identity to widen authorization. Canonical subscription identity is SHA256 of `[ownerUID, URL, eventName, sessionID, executionID-or-null]`, so argument object key order does not create duplicates. Closing blocks new executions and edits, confirms child exits, and emits ordered closing/exit/closed events before metadata removal. Existing unexpired leases retain terminal delivery through bounded execution/journal history; closed leases can retry their retained batch but cannot extend expiry or create new subscriptions. No separate permanent tombstone is stored. Unsubscribe remains idempotent after close.

Before sending application data, the server sends a signed, unique, single-use verification challenge and requires a constant-time matching echo with a 2xx status. Failure returns JSON-RPC `-32015`, with a sanitized reason. Successful verification is cached for that owner and URL for five minutes. Production callbacks require public HTTPS on port 443. Every connection resolves and checks all addresses, pins them to preserve TLS hostname checking, refuses private/link-local/metadata IPs, ignores proxy environment variables, and follows no redirects. DNS and transport timeouts are bounded. Loopback HTTP is enabled only inside compiled test fixtures.

Webhook body fields are `eventId`, `name`, ISO timestamp, `data`, and `cursor`. `data` contains a bounded events array, `catch_up_required`, and `earliest_cursor`. Subscribe to the project before starting work for ordinary push delivery. start_execution returns a cursor captured at its start, so recovery includes even output produced before the RPC response arrives. Each nested event has a monotonic broker sequence, execution/session ID, occurrence timestamp, kind, and structured data. The application gap flag indicates journal loss; catch up with `read_execution`. There is no unsupported protocol control message.

Headers use Standard Webhooks: `webhook-id`, `webhook-timestamp`, `webhook-signature` over `id.timestamp.exactBodyBytes`, plus `X-MCP-Subscription-Id`. A batch is serialized once and stored before sending. Retries keep its eventId and exact body, signing with the current attempt timestamp; duplicate and out-of-order receipt is expected. A rotated secret overlaps with the old secret for five minutes. Consumers must verify signature and timestamp and deduplicate events/sequences. A 2xx is receipt, not proof of execution or application acknowledgement.

Each lease is finite, at most 24 hours (default 24 hours), with a one-second minimum/rounding floor. `refreshBefore` is the granted expiry. Refresh retains an unacknowledged batch and resumes bounded retries without skipping its cursor. Only one pending batch per subscription and eight subscriptions are admitted. Complete bodies are limited to 64 KiB, below the 256 KiB platform limit. Transient transport errors, 429 and 5xx retry with exponential backoff, at most five attempts; 410/413 remove the lease without retry. Other 4xx or exhausted retries suspend the subscription with its pending batch retained. Explicit refresh can resume it.

Private 0700/0600 storage contains owner, filter, URL, signing key, expiry, last acknowledged cursor and the exact pending body. Atomic rename and fsync preserve the acknowledged state; a restarted broker reloads it and resumes delivery. Event history itself lives in broker memory; a broker restart changes its epoch and produces an application gap. This is bounded recovery, not unlimited durable output storage. Delivery workers never participate in the child pipe reader, so slow callbacks cannot block command output. Workers stop on lease expiry or loss of bounded retained history; failures require refresh or cursor recovery. Existing leases can receive terminal events after project metadata removal.

`input_execution` returns an accepted input sequence. Later Events distinguish successful OS write (`written`) from uncertain/partial delivery (`delivery_unknown`), also retaining the latest input receipt in the execution record. Neither status proves that a program interpreted the input. Lost responses, duplicate Events and silence never justify automatic input retransmission or declaring input-wait. For pipes, close_stdin=true closes the write descriptor after its queued text; text may be omitted for EOF only. Receipt includes stdin_closed. This is separate from a literal PTY Ctrl-D. Signals have a separate bounded control queue and can interrupt blocked stdin, marking a partial input uncertain. No execution/input API is automatically retried by this server.

A webhook 2xx proves receipt only, not which event fields reach a model or that a conversation resumed.
